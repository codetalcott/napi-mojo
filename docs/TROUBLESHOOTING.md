# Troubleshooting: a prebuilt addon will not load

This page is for anyone whose `require()` of a napi-mojo-built addon fails
while the native binary loads — whether that is `napi-mojo/demo` or an addon
someone else built with napi-mojo. You do not need Mojo installed, and you do
not need to rebuild anything: every failure below is about the machine or
container image the binary is loaded on.

Addons whose loader was generated by `napi-mojo release --scaffold` (and
`napi-mojo/demo` itself) rethrow these failures with an error `code` and a link
to the matching section here. The loader's original message is kept as the
error's `cause` and quoted in its text.

## Which images work

Linux prebuilds need **glibc 2.35 or newer** and the host's **C++ runtime**
(`libstdc++.so.6`, `libgcc_s.so.1`). Node links the C++ runtime itself, so any
Node image that meets the glibc floor has it. **Bun and Deno do not**, so under
them it depends on the image.

Rows marked *checked on every release* are loaded, or refused, by the
`consume-oldest-linux` job in `publish.yml` on both linux-x64 and linux-arm64
before anything is published. The other rows were measured once, from the
image contents, on 2026-09-13.

| image | runtime | status |
|---|---|---|
| `node:22-bookworm` | Node | checked on every release |
| `oven/bun:1.3.11-slim` | Bun | checked on every release |
| `denoland/deno:distroless-2.9.6` | Deno | checked on every release |
| `oven/bun:1.3.11-distroless` | Bun, with the [two-line fix](#fix-copy-the-c-runtime-in) | checked on every release |
| `oven/bun:1.3.11-distroless` | Bun, unmodified | does not load: [no C++ runtime](#missing-cpp-runtime) (the refusal is checked on every release) |
| `node:22-bullseye` | Node | does not load: [glibc 2.31](#glibc-too-old) (the refusal is checked on every release) |
| `oven/bun:1.3.11` | Bun | loads (measured) |
| `denoland/deno:2.9.6`, `denoland/deno:debian-2.9.6` | Deno | loads (measured) |
| `denoland/deno:ubuntu-2.9.6` | Deno | loads, exactly at the glibc floor (measured) |
| `denoland/deno:alpine-2.9.6` | Deno | does not load: [no C++ runtime](#missing-cpp-runtime) in its glibc layer |
| `oven/bun:1.3.11-alpine`, any Alpine image | any | does not load: [musl](#musl) |

## Catch it when the image is built, not when it is deployed

A load failure is a property of the image, so check it in the image: add a
line to the **final** stage of your Dockerfile that loads the addon. The build
then fails — with the explanation — instead of the deployed service. The exec
form (`["…"]`) needs no shell, so it works on distroless images too.

```dockerfile
# Bun
RUN ["bun", "-e", "require('your-addon')"]

# Node
RUN ["node", "-e", "require('your-addon')"]

# Deno: a one-line file containing  require('your-addon')
RUN ["deno", "run", "--allow-all", "check-addon.cjs"]
```

A `postinstall` script is not a substitute. Bun and Deno do not run
dependencies' lifecycle scripts by default, and in a multi-stage build the
stage that installs packages is usually not the image that runs them — so it
would check the wrong machine.

<a id="missing-cpp-runtime"></a>

## `libstdc++.so.6: cannot open shared object file`

Error code `ERR_NATIVE_NO_CXX_RUNTIME`. The loader may name `libgcc_s.so.1`
instead:

```
libstdc++.so.6: cannot open shared object file: No such file or directory
```

The image has no C++ runtime. The Mojo runtime inside the prebuilt package
needs one, and the package relies on the system's copy rather than shipping its
own (which keeps it about a tenth of the size). Node always has it; Bun and
Deno do not need it themselves, so minimal images leave it out.

**Fix: use an image that has it.** `oven/bun:*-slim` is the smallest Bun image
that does; `denoland/deno:distroless` is itself a distroless image that does.

### Fix: copy the C++ runtime in

To keep `oven/bun:*-distroless`, copy the two libraries from Google's
distroless `cc` image, which is built on the same Debian release:

```dockerfile
FROM oven/bun:1.3.11-distroless
COPY --from=gcr.io/distroless/cc-debian13 \
     /usr/lib/*-linux-gnu/libstdc++.so.6* /usr/lib/*-linux-gnu/libgcc_s.so.1 /opt/cxx-runtime/
ENV LD_LIBRARY_PATH=/opt/cxx-runtime
```

The wildcard picks up the right architecture on both amd64 and arm64. Match
the `cc` image's Debian release to your base image's (`oven/bun` 1.3 is
Debian 13). This exact recipe is built and loaded on every release, on both
architectures.

For `denoland/deno:alpine`, switch to `denoland/deno:distroless` rather than
patching it: its glibc compatibility layer is not a normal glibc install, and
a copied libstdc++ is not a tested configuration.

<a id="libstdcxx-too-old"></a>

## `` version `GLIBCXX_3.4.30' not found ``

Error code `ERR_NATIVE_LIBSTDCXX_TOO_OLD`.

```
/lib/x86_64-linux-gnu/libstdc++.so.6: version `GLIBCXX_3.4.30' not found (required by …/libKGENCompilerRTShared.so)
```

The image has a C++ runtime, but an older one than the Mojo runtime was built
against. `GLIBCXX_3.4.30` is GCC 12's, shipped by Ubuntu 22.04, Debian 12 and
anything newer. Every mainstream distribution with a new enough glibc (next
section) also has a new enough libstdc++, so this usually means a custom image
that pairs a new glibc with an old libstdc++. Use a stock Debian 12+ or Ubuntu
22.04+ base.

<a id="glibc-too-old"></a>

## `` version `GLIBC_2.35' not found ``

Error code `ERR_NATIVE_GLIBC_TOO_OLD`.

```
/lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.35' not found (required by …/libAsyncRTRuntimeGlobals.so)
```

The system's glibc is older than the Mojo runtime requires. glibc is the
system loader itself, so no package can bring its own copy: the host or base
image must be **Ubuntu 22.04, Debian 12, RHEL 9 or newer**. `node:22-bullseye`
(Debian 11) and Amazon Linux 2 are too old.

<a id="musl"></a>

## Alpine and other musl systems

Error code `ERR_NATIVE_MUSL`. The loader's message varies — often
`Error loading shared library libstdc++.so.6` or `Error relocating` — and
installing `libstdc++` does not help.

The prebuilt binaries are built for glibc, and there is no musl build of the
Mojo runtime to build against. Use a Debian- or Ubuntu-based image instead:
`node:22-bookworm-slim`, `oven/bun:*-slim` or `denoland/deno:distroless`.

## For addon authors

`napi-mojo release --scaffold` writes `load-error.js` beside your loader and
calls it when the binary fails to load, so your users get the explanations
above under your package's name. Re-running the scaffold refreshes it. If you
wrote your own loader, copy `load-error.js` from the napi-mojo package and wrap
your `require()`:

```js
const { explainLoadError } = require('./load-error.js');
try {
  module.exports = require(binaryPath);
} catch (err) {
  throw explainLoadError(err, { name: 'your-addon' });
}
```
