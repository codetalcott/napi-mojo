napi-mojo prebuilt platform package — what is inside, and under what terms
==========================================================================

The `@napi-mojo/<platform>` packages are not source. Each ships a compiled
`index.node` together with the runtime libraries it needs, so that installing
it requires no Mojo toolchain. Those libraries are third-party works. This
file records what they are; the full licence texts are beside it.

MODIFICATION NOTICE (Apache License 2.0, section 4(b)): each of these files
has been changed by `scripts/bundle-runtime.sh`. Its install name and rpath
(Mach-O) or RUNPATH (ELF) were rewritten so the set resolves beside itself
rather than in the directory it was built in, and on macOS each was re-signed
ad-hoc because arm64 invalidates a code signature on any Mach-O edit. No
source was changed and nothing was recompiled: the executable code is
byte-for-byte as Modular built it.

A note on the licence, recorded because it will be asked again. Modular's
compiler and tooling were open-sourced on 2026-08-18 under Apache 2.0 with
LLVM Exceptions, and the runtime sources are in that repository. The wheel
that ships the prebuilt binaries, however, declares
`LicenseRef-MAX-Platform-Software-License` in its metadata. The likeliest
explanation is stale wheel metadata — Mojo 1.0.0 shipped the same day as the
relicensing — and this notice follows the source licence. The sibling
mojo-http reached the same conclusion for the same files; see its
docs/FFI_DISTRIBUTION.md for the longer argument.


What the Linux packages do NOT carry
------------------------------------

Up to and including 0.13.0 the Linux packages also bundled GCC's
`libstdc++.so.6` and `libgcc_s.so.1`, copied from the pixi environment the
Mojo runtime was built against. They no longer do. Measured on the
published linux-x64 0.13.0 package, that is 26.1 MB -> 2.4 MB unpacked and a
9.4 MB -> 0.9 MB tarball: 91% smaller, either way.

They were redundant, for a reason that is a property of the artifact rather
than an assumption. The Mojo runtime requires at most `GLIBCXX_3.4.30`, and
it also requires `GLIBC_2.35` — which cannot be bundled, because glibc is the
dynamic loader. Every mainstream distribution new enough to satisfy the glibc
floor already ships a libstdc++ at 3.4.30 or better, and Node itself is a C++
program linked against both libraries, so they are present wherever a Node
process runs. Bun and Deno do not link libstdc++, so under those runtimes the
container image must provide it: oven/bun:*-distroless and
denoland/deno:alpine do not, and cannot load these packages.

That ordering is now enforced rather than believed:
`scripts/check-glibc-floor.mjs` fails the build if the Mojo runtime's GLIBCXX
requirement ever rises above what its own glibc floor guarantees on the worst
host that floor admits, and `publish.yml`'s `consume-oldest-linux` job loads
the real bundle in a Debian 12 container with no toolchain and asserts it is
refused below the floor. See docs/plan-distribution.md.

**Consequence for this file**: no part of any napi-mojo package is under the
GPL, with or without the GCC Runtime Library Exception. If you are auditing a
tarball published at 0.13.0 or earlier, it does contain those two libraries,
and the exception is what permitted their redistribution.


Verifying this file
-------------------

`scripts/check-platforms.mjs` asserts that each platform package declares a
licence covering what it ships and carries these files. It cannot tell you
that the list above is complete — `scripts/bundle-runtime.sh` discovers the
dependency closure at build time, so a toolchain change can add a library.
`build/bundled-libs.txt` in a release run is the authoritative list for that
run; if it names something not described here, this file is out of date.
